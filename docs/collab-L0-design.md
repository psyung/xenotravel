## 1. 동기화 서비스 비교

확인한 사실은 2026-11-25에 공식 페이지에서 다시 읽은 값이다. "미확인"은 아직 확인하지 못한 것이다.

| 항목 | A. Supabase (문서의 1순위) | B. Cloudflare Durable Objects + y-partyserver | C. 직접 운영 y-websocket (Fly.io 등) |
| --- | --- | --- | --- |
| 무료 한도 | 프로젝트 2개, DB 500MB, 파일 1GB, 전송 5GB(+캐시 5GB), MAU 5만, Realtime 동시 연결 200 · 월 메시지 200만 · 메시지 최대 256KB (supabase.com/pricing) | 미확인 (Workers 무료 플랜에 Durable Objects 포함 여부·한도 확인 필요) | 서버 1대 비용. 무료 등급은 서비스마다 다름 |
| 유료 | Pro $25/월부터 (8GB, 전송 250GB, 동시 연결 500, 월 메시지 500만) | 미확인 | 월 몇 달러부터 |
| 일시 정지 | **무료 프로젝트는 1주일 사용이 없으면 정지** (Pro는 정지 없음) | 없음(요청 기반) | 없음 |
| Yjs 연결 | `@supabase-labs/y-supabase` (GitHub `supabase-community`, MIT). 별 9개·포크 4개, 릴리스 날짜 확인 안 됨 → **작은 커뮤니티 라이브러리** | `y-partyserver` (npm 페이지 접근 거부로 미확인) | `y-websocket` 공식 |
| 문서 저장 | `SupabasePersistence`가 `yjs_documents(room, state)` 표에 문서 전체를 1초 디바운스로 저장 | Durable Object 저장소 | 직접 구현 (LevelDB 등) |
| 권한(초대 토큰) | ⚠ 라이브러리가 브라우저에서 표에 **직접** 쓰는 구조라, "토큰을 확인한 요청만 허용" 하려면 RLS + Edge Function으로 감싸거나 저장 부분을 직접 만들어야 함 | 서버 코드에서 토큰 확인을 직접 넣기 쉬움 | 서버 코드에서 직접 |
| 중국·한국·일본 연결 | **미실시** (아래 3번) · `*.supabase.co`가 일부 국가에서 막힌 사례 보고 | **미실시** · Cloudflare는 중국 본토에서 느리거나 불안정한 경우가 있음 | 리전에 따라 다름 |
| 데이터 삭제 | 표의 행 삭제 + 백업 보존 기간(플랜별) | Durable Object 삭제 | 직접 |
| 운영 부담 | 낮음 (단, 정지 방지 크론 필요) | 낮음~중간 | 높음 (서버 관리) |

**권장:** A(Supabase)로 시작하되 **Yjs 연결은 `y-supabase`를 그대로 쓰지 않고 얇게 직접 만든다.** 업데이트는 Edge Function 하나(`/sync`)가 초대 토큰 해시를 확인한 뒤 표에 쓰고, 실시간 전달만 Realtime broadcast를 쓴다. 라이브러리가 작고 오래 유지될지 불확실하며, 브라우저가 표에 직접 쓰는 구조는 토큰 확인과 맞지 않기 때문이다. Supabase 주소는 설정값 하나(`SYNC_ORIGIN`)로 두어, 막히는 나라가 생기면 내 도메인 프록시나 B로 바꿀 수 있게 한다.

**지금 앱이 정적 호스팅(서버 없음)이라는 점:** 토큰 확인·정지 방지 크론은 Supabase Edge Function과 Vercel Cron(무료)으로 처리한다. Vercel에 `/api`를 새로 만들 필요는 없다.

## 2. 데이터 모델: 지금 `trip` JSON ↔ Yjs 문서

여행 하나 = Y.Doc 하나. 맨 위는 `Y.Map('trip')`.

| 지금 필드 | Yjs 형태 | 비고 |
| --- | --- | --- |
| `id`, `version`, `createdAt` | 일반값 | 처음 만들 때 한 번 |
| `title`, `destination`, `startDate`, `endDate`, `center`, `country`, `trendCity` | 일반값 (Y.Map의 키) | 마지막에 쓴 값이 이김 |
| `days[]` = `{ id, date, travelMode, items[] }` | `Y.Array<Y.Map>` · `items`는 `Y.Array<Y.Map>` | 순서 바꾸기·같은 날 동시 끌기가 합쳐진다 |
| 장소(`items[]`, `inbox[]`) = `{ id, name, lat, lng, time, memo, url, category, visited, cost, … }` | `Y.Map` (필드마다 키) | `memo`는 일반 문자열(동시에 같은 메모를 고치면 마지막 값). 글자 단위 합치기(Y.Text)는 MVP에서 안 함 |
| `inbox[]` | `Y.Array<Y.Map>` | |
| `stays[]` | `Y.Array<Y.Map>` | `startIndex`·`nights`는 일차 번호 기준 → 날짜 변경은 소유자만(L-2) |
| `flights[]` | `Y.Array<Y.Map>` | |
| `checks[]` | `Y.Array<Y.Map>` | |
| `expenses[]` | `Y.Array<Y.Map>` | `payer`·`split` 포함 (아래 결정 3) |
| `budget` | `Y.Map` | 기준 통화·예산 |
| `members[]` (정산 동행자) | `Y.Array<Y.Map>` | 공동 편집 참여자와 연결 (결정 3) |
| **`segments{}` (J-10, 새로 생김)** | `Y.Map<'fromId>toId', 일반값>` | 구간 하나가 키 하나. 두 사람이 다른 구간을 고치면 둘 다 남는다 |
| 커버 사진 | **동기화 안 함 (MVP)** | 지금은 IndexedDB(`xenotravel-covers`)의 기기 전용. 공유하려면 파일 저장소가 따로 필요 |
| `updatedAt` | 쓰지 않음 | Yjs가 변경 기록을 가진다 |
| 새 필드: 항목별 `updatedBy` | 각 Y.Map의 키 | 참여자 ID. 장소 카드 이니셜 표시용 |
| 새 필드: 항목별 `private` | 키 | "나만 보기" 항목은 서버에 올리지 않고 기기에만 둔다 |

**선반영(데이터 마이그레이션) 판단:** 문서는 "L-1 전에 모든 항목에 id·`updatedBy`·`paidBy`를 넣자"고 했지만, 확인해 보니 일차·장소·숙소·항공편·체크·지출에 **이미 모두 고유 id가 있다.** 지출의 "낸 사람"도 N빵 정산 때 만든 `payer` 필드가 있다. 그래서 지금 개인 여행에 미리 넣을 필드는 없다고 본다. `updatedBy`는 혼자 쓰는 여행에서는 의미가 없으니 공동 편집을 켤 때 채운다. (결정 3에서 `payer`를 그대로 쓰기로 하면 이 판단이 맞다.)

## 결정할 것

1. **서비스:** Supabase로 시작하되 Yjs 연결·저장은 얇게 직접 만든다(라이브러리 그대로 쓰지 않음). 괜찮은가?
2. **Supabase 계정:** 프로젝트는 사용자 계정으로 만들어야 한다(키·결제 정보가 사용자 소유). 만들어 주면 anon key와 URL만 받아 설정에 넣는다. service_role 키는 Supabase Edge Function 환경변수에만 넣고 레포·채팅에는 넣지 않는다.
3. **낸 사람 필드:** 문서의 `paidBy` 대신 이미 있는 `payer`(정산 동행자 id)를 그대로 쓰고, 공동 편집 참여자를 정산 동행자(`members`)와 연결한다. 괜찮은가?
4. **보기 전용 역할:** MVP에서는 따로 만들지 않고 지금의 읽기 전용 공유 링크를 쓴다. 괜찮은가?
5. **보유 기간:** 마지막 접속 후 1년 삭제 · 30일 전 안내 · 즉시 삭제 시 백업 7일. 이대로 갈까?
6. **리전:** 3번 연결 테스트 후 서울/도쿄 중 정한다. 중국 테스트를 해 줄 수 있는가(본인 또는 현지 지인)?
7. **커버 사진:** MVP에서는 동기화하지 않는다(기기마다 따로). 괜찮은가?
